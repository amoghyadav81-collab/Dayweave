# Security model

- Passwords: unique random salt + Node scrypt; 12–256 characters. No third-party auth headers are trusted. Email is not verified; registration is gated by an operator invitation. No public mail/password recovery provider is assumed. Authenticated password changes revoke other sessions, pending authorization codes and OAuth grants; account deletion requires password plus explicit confirmation and deletes only that user’s records.
- Browser sessions: opaque 256-bit random values, SHA-256 stored in SQLite; seven-day expiry, HttpOnly, SameSite=Lax, Secure on HTTPS. Mutations verify Origin against configured APP_URL, never forwarded Host. API payloads have bounded streaming reads. Account scope is checked in addition to server-derived user identity.
- Isolation: the authenticated server-side user ID selects every planner row. Caller-supplied IDs/headers cannot select another workspace. Browser cookies do not authorize MCP. Bearer credentials do not authorize browser APIs.
- OAuth: RFC 8414 metadata, RFC 9728 protected-resource metadata, RFC 7591 public-client registration against exact administrator-configured redirect URIs, authorization-code S256 PKCE, user consent and explicit `planner` scope/resource. Maintained `@node-oauth/oauth2-server` 5.3.1 processes authorization, code/PKCE/token exchange, bearer validation and refresh rotation; application adapters enforce fixed audience, exact redirects and hashed server-side storage. Client name is unverified metadata and is HTML-escaped. The operator must trust the redirect allowlist. Only public clients are implemented, not confidential client secrets or arbitrary client-ID metadata documents.
- Codes: five-minute expiry, exact client/redirect/resource binding, single-use code consumption. The maintained library consumes a code before PKCE/redirect verification, so a failed attempt requires restarting authorization. Token-pair/grant storage is transactional. State is round-tripped; authorization responses include issuer.
- Tokens: opaque high-entropy bearer tokens, SHA-256 stored; access 15 minutes, refresh 30 days; explicit resource binding at issue and refresh, implicit fixed audience `/mcp`. Refresh rotates once; detected reuse by the bound client revokes the whole grant. Revocation checks the issuing client and invalidates the grant. Account revocation is user-scoped. Every MCP request checks expiry and revocation in SQLite; no JWT trust shortcuts.
- Writes: all mutations require the previous version, including delete, undo and preferences. Conditional SQLite writes reject stale reads. Every AI mutation requires an operationId; write/history, receipt and inverse commit together. AI recovery is receipt-specific and checks touched records; completed and fixed protections cannot be bypassed through recovery/import/timezone changes. Intentional manual undo/restore is separate. Full details and receipt quotas are in RELIABILITY-CONTRACT.md. No blind automatic retry changes a plan.
- Rate limits: persistent per-email/global authentication windows and client-registration limits bound a modest invite-only service. Invitations are validated before registration consumes a budget, and invited signup has separate per-email/global budgets from sign-in, so rejected invitations cannot lock out existing users. Sign-in still has a coarse shared limit: unauthenticated password attempts can exhaust it for the service. Put a reverse proxy in front with connection/body/request limits and configure no caching for authenticated routes; the application does not trust caller-supplied IP headers. These controls are not a large public-service abuse system. No high-volume public signup, billing or paid external APIs are enabled.
- Recovery: planner JSON export/merge is per-user and authenticated. Full database backups contain *all* users, password hashes, sessions and tokens; encrypt/access-control them. On restoring an old DB revoke all sessions/grants before exposing service, because credentials revoked after that snapshot could otherwise reappear.
- Secrets: invitation code belongs in host secrets/environment settings, never committed. Data is not end-to-end encrypted; use host disk encryption/backups and TLS. Optional browser snapshots are unencrypted and scoped to a verified account. Auth failure/account mismatch clears the previous view/cache, and logout/deletion sends Clear-Site-Data. Avoid snapshots on shared devices. No analytics or external font requests are required.

This is an invite-only beta, not a completed independent security audit. No MFA, email verification, self-service recovery, native alarms, automatic data-retention policy or distributed rate limiter is included. For broader release, add appropriate operator privacy/contact/retention disclosures and terms, operational monitoring and independent review. Hosting/TLS and live client behavior remain unverified until deployed checks pass.
